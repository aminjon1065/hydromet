# Портал экологического мониторинга Гидромета

Репозиторий содержит спецификацию и развиваемую реализацию нового
самостоятельного портала.

## Зафиксированные решения

- Портал создаётся как новая кодовая база; работы с существующим `meteo.tj` не влияют на основную архитектуру и оценку.
- Гидромет предоставляет реестр станций, текущие и исторические наблюдения, SmartMet endpoints и данные MeteoAlert.
- SILAM подключается через адаптивный iframe `https://silam.fmi.fi/roux/TAJ/`; локальная обработка NetCDF/GRIB, COG и GeoServer не выполняется.
- Портал приводит внешние форматы к собственной канонической модели, хранит локальную копию нужных данных и показывает состояние/давность источников.
- Рекомендуемый стек: Laravel 13, Inertia.js + React + TypeScript, shadcn/ui, Filament 5, PostgreSQL/PostGIS, React-Leaflet, ECharts, Redis и Docker Compose.
- Архитектура — модульный монолит с адаптерами внешних источников, без NestJS, микросервисов, Kafka и Kubernetes.
- Первый production-год портал работает на VPS подрядчика; резервные копии должны храниться вне этого VPS.

## Основной вывод по `smartmet-alert-client`

Репозиторий FMI — качественный Vue-компонент для пятидневной SVG-карты предупреждений, но не готовый движок нашего портала. В нём жёстко заданы финские WFS-слои, геометрии регионов, языки `fi/sv/en`, часовой пояс Helsinki и специфический формат flood warnings.

Основная рекомендация: хранить предупреждения в канонической CAP-совместимой модели и показывать их полигоны на общей Leaflet-карте портала. `smartmet-alert-client` использовать как референс интерфейса, иконок, уровней опасности и accessibility. Если заказчик потребует именно пятидневную FMI-карту, её адаптация оформляется отдельным пакетом работ.

## Оценка

- Основной MVP: 6–8 недель одному разработчику либо 4–6 недель двум.
- Полный приёмочный объём с AQI, аудитом исправлений, CMS, тремя языками, безопасностью, тестами, документацией и обучением: 9–12 недель одному либо 7–9 недель двум с part-time QA/переводчиком.
- Риск по срокам: ещё 1–3 недели, если история загрязнена, форматы источников меняются, нет геометрий регионов или задерживается утверждение переводов/AQI.

## Что нужно до интеграции реальных данных

Минимальный стартовый пакет от Гидромета:

1. пример реестра станций;
2. пример текущих измерений;
3. часть исторических данных;
4. перечень параметров, единиц и quality flags;
5. пример MeteoAlert `Alert`, `Update` и `Cancel`;
6. полигоны предупреждений либо официальный GeoJSON административных границ;
7. SmartMet URL, producer, параметры и тестовый доступ;
8. утверждённая формула AQI либо согласие временно отключить AQI.

После получения этих данных либо утверждения mock-контрактов можно создавать Laravel-приложение, миграции и первые адаптеры без архитектурных догадок.

## Статус разработки

Фаза 1 (основание приложения) выполнена: модульный монолит Laravel, публичная
оболочка Inertia + React + TypeScript с shadcn/ui, административная панель
Filament, Docker Compose (Nginx, PHP-FPM, очередь, планировщик,
PostgreSQL/PostGIS, Redis), health-эндпоинт и инструменты контроля качества
(Pint, PHPStan/Larastan, ESLint, TypeScript, PHPUnit, Vitest).

Фаза 2A (каталог станций и параметров) выполнена на **mock-данных**: таблицы
`stations`, `parameters`, `station_parameter`, канонические записи из
`docs/03-data-contracts.md`, граница интеграции `StationRegistryProvider` с
fixture-адаптером, идемпотентный сервис импорта реестра и read-only ресурсы
Filament. Реальные данные Гидромета не получены.

Фаза 2B (хранение измерений и правки источника) также выполнена на
**mock-данных**: таблицы `measurements` и `measurement_revisions`, каноническая
запись измерения, граница `MeasurementProvider` с fixture-адаптерами (базовый
пакет и пакет коррекции) и идемпотентный сервис импорта, который применяет
правки источника, сохраняя исходно переданное значение.

Фаза 2C (журнал источников и синхронизаций) добавляет таблицы
`integration_sources`, `synchronization_runs` и `synchronization_rejected_rows`
и сервис `SynchronizationRunner`. Обе fixture-команды выполняются через него,
поэтому каждый запуск оставляет запись со статусом, счётчиками и отклонёнными
строками. Секреты не хранятся: таблица источников не имеет колонок для учётных
данных, а сообщение и trace исключения не попадают ни в журнал, ни в лог — в
журнале остаются стабильный `error_code` и безопасная формулировка, в логе —
только id запуска, код источника, вид импорта и класс исключения.

Фаза 2D добавляет в Filament доступные только для чтения разделы источников
интеграции (`/admin/integration-sources`) и запусков синхронизации
(`/admin/synchronization-runs`). Оператор видит настройки без секретов,
состояние и счётчики запуска, курсоры и безопасные сведения об отклонённых
строках. Маршруты создания, изменения и удаления для этих ресурсов отсутствуют.

Фаза 2E добавляет сверку агрегатов fixture-набора: количество станций и
измерений по станции/параметру, временные границы, пропуски, невалидные или
сомнительные значения и ревизии. Фаза 2F добавляет ограниченные UTC-окна
синхронизации, сохранение курсоров и настраиваемое перекрытие; fixture-тест
доказывает, что поздняя правка источника попадает в следующее окно без дублей.

Безопасная mock-часть Фазы 3 также реализована: публичная Leaflet-карта с
текущими значениями, локализованная страница станции, графики ECharts за 24
часа, 7 и 30 дней и 1 год, выбор параметра и потоковый CSV для того же периода.
Невалидные значения исключаются, пропуски остаются разрывами и не становятся
нулями, исправления источника отмечаются. SILAM открыт отдельной страницей через
iframe предоставленного FMI URL с резервной внешней ссылкой. Все fixture-экраны
явно помечены как искусственные данные.

Добавлен локальный CMS: неполный материал можно сохранить как черновик, но для
публикации обязательны заголовок и текст на `tj`, `ru`, `en`, а дата может быть
отложенной. Текст не исполняется как HTML. Администратор и редактор могут
создавать и изменять материалы, оператор видит их только для чтения. Создание и
изменения записываются в неизменяемый журнал before/after, доступный в Filament
только администратору по временной least-privilege матрице ролей. Опубликованные
материалы доступны как `/content/{slug}` и `/api/v1/content/{slug}`.

Фаза 2G добавляет вертикальный срез MeteoAlert на **mock-данных**: каноническая
модель предупреждений с полным жизненным циклом CAP `Alert`/`Update`/`Cancel` и
сохранением истории сообщений, provider-нейтральная граница `AlertProvider` с
fixture-адаптером, идемпотентный импорт через существующий журнал синхронизаций,
эндпоинты `/api/v1/alerts` и `/api/v1/alerts/{identifier}`, слой полигонов на
существующей карте станций вместе с доступным с клавиатуры списком
предупреждений и легендой, а также раздел Filament только для чтения.

Предупреждения — вымышленные демонстрационные данные и помечены как таковые на
всех трёх языках на каждом экране. Источник MeteoAlert ещё не выбран, поэтому
реального адаптера нет. Коды явлений имеют префикс `FIXTURE_`, а цвета уровней
опасности — предварительный выбор портала, а не утверждённая национальная шкала.

Защита ответов реализована и покрыта тестами: базовые security-заголовки и
Content Security Policy на каждом ответе, включая ошибки и несуществующие
маршруты; разрешение iframe для SILAM выводится из настроенного URL и при
некорректном значении остаётся закрытым; ошибки API никогда не раскрывают
исключение, stack trace или учётные данные, даже при включённом `APP_DEBUG`;
отдельная проверка проходит по всем зарегистрированным маршрутам панели и
доказывает, что ни одна её страница недоступна гостю или отключённому
пользователю.

Каждый публичный ответ несёт nonce в `script-src`, уникальный для запроса:
внедрённый скрипт не выполнится, если не содержит непредсказуемое значение. Для
стилей по умолчанию действует `'self' 'unsafe-inline'`; переключатель
`CSP_STYLE_NONCE=true` переводит их на nonce, но тогда обязательна директива
`style-src-attr 'unsafe-inline'` для инлайновых атрибутов стиля, которые
проставляет Leaflet — почему это не значение по умолчанию, описано в
`config/security.php`. Административная панель работает по отдельной, более
слабой политике: Filament отдаёт inline-скрипты без поддержки nonce, а Alpine
вычисляет выражения через `new AsyncFunction`.

Администратор может выгрузить неизменяемый журнал аудита в CSV прямо из панели.
Файл не зависит от языка интерфейса, его ячейки не выполняются как формулы
электронной таблицы, а сама выгрузка записывается в журнал.

Управление учётными записями реализовано на предварительной модели трёх ролей:
администратор создаёт записи, назначает роль, включает и отключает доступ и
задаёт пароль — всё через один доменный сервис с обязательным аудитом. Панель не
позволяет отключить или понизить последнего активного администратора, а также
отключить себя или изменить собственную роль. Учётные записи отключаются, а не
удаляются, поэтому их журнал аудита сохраняет автора действий; это обеспечивают
и модель, и триггер базы данных. Отключение записи, изменение роли и смена
пароля завершают её существующие сессии уже на следующем запросе — через
служебную отметку в самой учётной записи, а не удалением строк сессий, поэтому
это работает при любом session driver. Пароли хранятся в виде хеша и никогда не
отображаются, не выгружаются и не попадают в журнал аудита. Первый администратор
создаётся одноразовой командой на пустой установке. Окончательная матрица ролей
и список пользователей всё ещё ожидаются от Гидромета, портал не содержит
администратора по умолчанию, а письма для сброса пароля заблокированы до
настройки SMTP.

`GET /api/v1/system/status` публикует, насколько актуальна копия каждого
включённого источника: код источника, состояние, время последнего успешного
импорта и утверждённый порог устаревания — и ничего о внутренней конфигурации.
Это не проверка работоспособности приложения: за неё отвечают `/up` и `/health`,
и именно их должен опрашивать мониторинг. Реальные пороги всё ещё ожидаются от
Гидромета, поэтому источник без утверждённого порога публикуется как `unknown`,
что намеренно не выдаётся за исправное состояние, а результаты на искусственных
данных не подтверждают промышленный уровень обслуживания.

Формат CSV остаётся предварительным до утверждения контрольного примера
Гидрометом. AQI, слои SmartMet, реальные адаптеры источников (в том числе
MeteoAlert), ручная коррекция измерений, расписание и повторные попытки,
утверждённые пороги устаревания и утверждённые материалы/навигация ещё не
реализованы. В `/api/v1` уже работают метаданные, список/карточка станций,
ограниченные временные ряды, CSV, опубликованный контент, предупреждения и
состояние источников на канонических локальных read-моделях.

## Разработка

Полный список команд — в [README.md](README.md#local-development). Кратко:

```bash
cp .env.example .env
docker compose build
docker compose run --rm --no-deps app composer install
docker compose run --rm --no-deps app php artisan key:generate
npm install && npm run build

docker compose up -d                              # запуск
docker compose exec app php artisan migrate       # миграции
docker compose exec app php artisan users:bootstrap-administrator   # первый администратор:
                                                  # только при полностью пустой таблице users,
                                                  # дальнейшие учётные записи — в панели

docker compose exec app php artisan stations:import-fixture-registry  # mock-реестр
docker compose exec app php artisan measurements:import-fixture-batch --scenario=base
docker compose exec app php artisan measurements:import-fixture-batch --scenario=correction
docker compose exec app php artisan alerts:import-fixture-feed --scenario=baseline
docker compose exec app php artisan alerts:import-fixture-feed --scenario=lifecycle
docker compose exec app php artisan data:reconcile-fixture

docker compose exec app composer test             # backend-тесты (SQLite)
docker compose exec app composer test:pgsql       # backend-тесты (PostgreSQL/PostGIS)
npm test                                          # frontend-тесты
composer check                                    # Pint + PHPStan + тесты
npm run lint && npm run types:check               # ESLint + typecheck

docker compose down                               # остановка
```

Портал доступен на `http://localhost:8080`, SILAM — на
`http://localhost:8080/silam`, административная панель — на
`http://localhost:8080/admin`. Ссылки на страницы станций появляются в
публичном обзоре после импорта fixture- или утверждённых production-данных.
Версионированный read API начинается с
`http://localhost:8080/api/v1/metadata` и
`http://localhost:8080/api/v1/stations`.
Опубликованные CMS-материалы открываются по
`http://localhost:8080/content/{slug}` и
`http://localhost:8080/api/v1/content/{slug}`.

Каждый запуск fixture-команды записывается в `synchronization_runs`
(docs/03-data-contracts.md, раздел 8). Строка источника `fixture` создаётся
автоматически при первом запуске, отдельный seeding не нужен:

```bash
docker compose exec postgres psql -U hydromet -d hydromet -c \
  "SELECT id, kind, status, received_count, accepted_count, rejected_count
   FROM synchronization_runs ORDER BY id"
```

Статус `succeeded` — отклонённых строк не было, `partial` — запуск завершился, но
часть строк отклонена, `failed` — запуск прерван неожиданной ошибкой. Повторный
запуск создаёт новую запись журнала и не меняет данные.

После импорта реестра, базового пакета и пакета коррекции команда
`data:reconcile-fixture` сравнивает базу с зафиксированными агрегатами. При любом
расхождении она завершается с кодом `1` и показывает все отличающиеся поля.
Команда запрещена в production и не является приёмкой данных Гидромета — для
неё Гидромет должен предоставить утверждённые итоги реального периода.

Команда `stations:import-fixture-registry` загружает искусственный
fixture-реестр под ключом источника `fixture`. Она идемпотентна, содержит одну
намеренно некорректную строку (частичный результат — это ожидаемое поведение) и
запрещена в окружении `production`.

`measurements:import-fixture-batch --scenario=base|correction` загружает
искусственные измерения того же источника; реестр станций должен быть
импортирован первым. Обе сцены идемпотентны: `correction` создаёт одну запись
в `measurement_revisions` и не меняет исходное значение. Опция `--scenario`
обязательна.

`alerts:import-fixture-feed --scenario=baseline|lifecycle` загружает
искусственные предупреждения. `baseline` содержит действующее предупреждение с
полигоном, предупреждение с двумя районами, истёкшее предупреждение, сообщение
со статусом `Test` (никогда не публикуется) и одну намеренно некорректную
строку. `lifecycle` присылает `Update` и `Cancel`: они заменяют и отменяют
предшественников, но сами предшественники остаются в истории. Обе сцены
идемпотентны, опция `--scenario` обязательна, команда запрещена в `production`.

### Изоляция тестов и CI

`tests/TestEnvironment.php` фиксирует cache, session, queue, mail и
broadcasting на изолированных драйверах до загрузки первого теста, поэтому
запуск на хосте и внутри Compose (который передаёт весь `.env` каждому сервису)
ведёт себя одинаково. База данных по умолчанию — SQLite в памяти; унаследованные
`DB_CONNECTION` или `DB_DATABASE` её не меняют.

Ограничения `CHECK`, триггеры неизменяемости и PostGIS проверяются только на
PostgreSQL. `composer test:pgsql` выставляет явный опт-ин `HYDROMET_TEST_DB=pgsql`,
использует служебную базу `hydromet_testing` и запускается с `--fail-on-skipped`.
Базу нужно создать один раз:

```bash
docker compose exec postgres psql -U hydromet -d postgres \
  -c "CREATE DATABASE hydromet_testing OWNER hydromet"
```

Попытка указать в `HYDROMET_TEST_DATABASE` рабочую базу приложения прерывает
запуск. Подробности — в [README.md](README.md#test) и
[docs/06-testing-and-acceptance.md](docs/06-testing-and-acceptance.md).

`.github/workflows/ci.yml` выполняет те же команды на каждый push в `master` и
каждый pull request: backend (Pint, PHPStan, SQLite-набор), backend на
PostgreSQL/PostGIS без пропущенных тестов и frontend (format, lint, types,
тесты, production-сборка). Артефакты не публикуются, деплой не выполняется.

### Аудит зависимостей

```bash
composer security         # весь locked PHP-дерево: любая advisory и abandoned пакет блокируют
npm run audit:production  # runtime-зависимости JS: moderate и выше блокирует
npm run audit:all         # runtime и dev JS: high и выше блокирует
npm run security          # оба npm-аудита подряд
```

| Экосистема | Область | Блокирует | Почему |
| --- | --- | --- | --- |
| PHP | Всё locked-дерево (`composer.lock`) | Любая advisory и любой abandoned-пакет | Backend обслуживает каждый запрос, а для заброшенного пакета advisory просто некому выпустить |
| npm | Только runtime-зависимости | `moderate`, `high`, `critical` | Они попадают в браузер или в обработку запроса |
| npm | Runtime и development | `high`, `critical` | Dev-дерево должно лишь корректно собирать и тестировать |

Аудиты читают `composer.lock` и `package-lock.json`, то есть проверяют именно
то дерево, которое разворачивается, и не требуют установленных зависимостей.
Они только сообщают: ни один script и ни один workflow не выполняет
`npm audit fix` или `composer update`. Разбор падения — вручную, процедура в
[`docs/09-runbooks.md`](docs/09-runbooks.md), раздел 8b.

На 2026-09-03 все три проверки дали ноль находок.

Пороги — **предварительная** политика, выбранная в пользу безопасности, а не
удобства. Должен ли аудит блокировать релиз и с какого уровня — решение
владельца
([`docs/08-hydromet-input-checklist.md`](docs/08-hydromet-input-checklist.md),
раздел 6).

Отдельный `.github/workflows/dependency-security.yml` выполняет те же команды на
pull request, push в `master`, по расписанию (понедельник, 04:17 **UTC** —
GitHub всегда считает cron в UTC) и по ручному запуску, а на pull request
дополнительно `actions/dependency-review-action@v4`. Прав у workflow только
`contents: read`, секреты не используются, комментарии в PR не публикуются,
зависимости не устанавливаются.

Все параметры Dependency Review заданы явно, потому что по умолчанию у action
`fail-on-scopes` включает только `runtime`: используются `fail-on-severity:
moderate`, `fail-on-scopes: runtime, development, unknown`,
`vulnerability-check: true` и `warn-only: false`. То есть `moderate` и выше
блокирует добавление уязвимых зависимостей во всех scopes — runtime,
development и unknown. Allowlist и исключений нет — ни в action, ни в
`composer.json`. Подробности — в
[`docs/06-testing-and-acceptance.md`](docs/06-testing-and-acceptance.md),
раздел 6.2.

Языковые ключи приложения — `tj`, `ru`, `en`, запасной — `ru`. Внутренний ключ

## Развёртывание

`compose.yaml` — **только среда разработки**. Он монтирует рабочую копию в
контейнеры через bind mounts, не содержит собранных ассетов и не подходит для
VPS как есть.

До первого развёртывания на VPS дополнительно требуется (в Фазу 1 не входит):

- production-образ, который копирует приложение внутрь, выполняет
  `composer install --no-dev --optimize-autoloader` и включает результат
  `npm run build`, вместо монтирования исходников;
- override `compose.prod.yaml` без bind mounts и без публикации портов
  PostgreSQL/Redis, с закреплёнными тегами образов и политиками перезапуска;
- терминация TLS, `APP_DEBUG=false`, кэш конфигурации/маршрутов/представлений;
- внешнее хранилище резервных копий и репетиция восстановления
  (`docs/01-product-scope.md`, раздел 3.4).

Порты PostgreSQL и Redis публикуются только на `127.0.0.1`. Контейнеры `app`,
`queue` и `scheduler` обращаются к ним по внутренней сети Compose как
`postgres:5432` и `redis:6379`.
